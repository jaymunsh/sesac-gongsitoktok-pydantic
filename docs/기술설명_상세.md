## 0. 한 줄 정리 (정직하게)
**"오케스트레이션(파이프라인 흐름)은 두 버전이 거의 같다. 진짜로 바뀐 핵심은 ①인제스트(표-인식+Contextual) ②검색(진짜 하이브리드) ③에이전트 프레임워크(무거운 CrewAI 래퍼 → 경량 PydanticAI)이다."**

## 1. "오케스트레이션"이란 / 기존 코드도 아키텍처화돼 있었나?

### 1-1. 오케스트레이션 = 서비스 레이어의 책임 (프레임워크가 아님)
오케스트레이션 = **여러 단계를 잇는 흐름**: `라우터 분류 → (스코프/스몰토크 분기) → 검색 + 재무결합 + 거시결합 → 작성 → 검증`.
이 흐름은 **두 버전 모두 `services/chat.py`(우리 코드)** 에 있다. CrewAI도 PydanticAI도 이 흐름을 "제공"하지 않는다 — 그냥 `if/else`, `await`, `asyncio.gather` 같은 **평범한 파이썬 제어흐름**이다.

> **그래서 "기존 코드도 아키텍처화 할 수 있나?"의 답: 이미 돼 있었다.** 기존 `handle_turn`도 라우터→가드→스몰토크→요약/QA→검증 흐름 + 재무·거시 결합 + 사전요약 트랙을 갖췄다. 오케스트레이션은 **프레임워크 독립적**이라, 프레임워크를 바꿔도 흐름은 그대로 가져올 수 있다.

### 1-2. 그럼 무엇이 바뀌었나 — 에이전트 "한 호출"을 감싸는 방식
차이는 흐름이 아니라 **각 LLM 호출을 어떻게 정의·실행하는가**다.

| | 기존 CrewAI | 재구축 PydanticAI |
|---|---|---|
| 에이전트 정의 | `Agent(role=…, goal=…, backstory=…)` **롤플레이** | `Agent(model, instructions=…, output_type=…)` **타입 선언** |
| 생성 시점 | **매 호출마다** Agent+Task+Crew **재생성** | **모듈 레벨 1회 정의·재사용**(싱글톤) |
| 실행 | `Crew(...).kickoff(inputs=…)` | `agent.run(prompt)` |
| 구조화 출력 | `output_pydantic=Model` (+ `_as_pydantic` 수동 추출) | `output_type=Model` (**네이티브 검증+자동 재시도**) |
| LLM 레이어 | litellm (`drop_params`로 o4-mini 파라미터 수동 제거) | provider 네이티브 |
| 멀티에이전트 기능 | **안 씀**(전부 단일-에이전트 Crew) → "단일 래퍼로 전락" | 동일하게 단일 목적, 단 경량 |

- **핵심**: 기존 "에이전트"는 사실 **구조화 출력 한 번 뽑으려고 CrewAI라는 무거운 팀-협업 프레임워크를 단일-에이전트로 쓴 것**. CrewAI의 역할분담·위임·협업은 하나도 안 썼다. PydanticAI는 "구조화 출력"이 1급 기능이라 **같은 일을 더 가볍게**(매 호출 객체 재생성 제거, litellm 우회, 네이티브 재시도) 한다.
- 즉 **프레임워크 교체의 이득 = 기능이 아니라 무게·관용구·유지보수성**. (기능 자체는 둘 다 "LLM→검증된 Pydantic 객체")

### 1-3. 정직한 인정 — 기존 코드가 이미 갖췄던 좋은 패턴들
재구축하며 "고친" 것 중 일부는 **기존 코드에도 이미 있었고**, 내가 다시 만든 것이다:
- **retrieve-then-read**(검색은 코드가 끝내고 근거를 프롬프트로) — 기존 `run_chat_qa`에 있었음
- **인용 정본화**(LLM이 고른 chunk_id를 검색 결과 원본으로 환원, quote 환각 차단) — 기존 `_reconcile`. 내가 "provenance 고정"으로 재발견
- **임계값 verdict**(grounded_score→pass/partial/fail를 코드로 확정) — 기존 `_verdict_from_score`. 내가 재발견
- **재무 결합·거시 결합·date 필터·prefer_recent** — 기존에 있었음
- **사전요약 트랙**(`summary_<corp>` precompute) — 기존에 있었으나 **본 재구축은 아직 미구현**(개선점, §6)

→ 결론: 기존 설계자는 RAG·검증·결합을 이미 잘 이해하고 있었다. **재구축의 진짜 가치는 "인제스트·검색 품질 + 프레임워크 현대화"** 이지, "없던 아키텍처를 새로 만든" 게 아니다.

## 2. 파이프라인 단계별 상세

### 2-1. 런타임(질문 1턴) 전체 흐름
```
ChatV2Request(v2.0) ──contract.to_internal──▶ ChatRequest
                                                  │
                                       [router_agent gpt-4o-mini]  ← 의도/스코프/검색쿼리/기간/플래그
                                                  │ RouterResult
                 ┌──── smalltalk/out_of_scope ────┤ (분기 즉시 응답)
                                                  │ qa / summary
                              ┌───── asyncio.gather (병렬) ─────┐
                       corpus 하이브리드 검색          재무결합(DART)        거시결합(ECOS, macro_relevant)
                       (벡터∪BM25 RRF→dedup→recency)  fnlttSinglAcnt       macro_snapshot
                              └──────────── 근거 합치기 ─────────┘
                                                  │ evidence(프롬프트)
                              [qa_agent gpt-5.1] 또는 [summary_agent gpt-4o-mini]  ← 근거 안에서만 작성
                                                  │ answer + (실제 검색근거로 provenance 고정)
                              [verifier_agent o4-mini]  ← 샘플링(질문 해시 20%) → grounded_score
                                                  │ verdict = 임계값(0.7/0.4)으로 코드가 확정
                 ChatResponse ──contract.to_v2──▶ ChatV2Response(answerText/sources/macroSnapshot/…)
                                                  │
                                         storage.save_chat (보관) → /api/analyses 로 조회
```

### 2-2. 노드별 역할·모델·구현 위치
| 노드 | 종류 | 모델 | 구현 | 비고 |
|---|---|---|---|---|
| router | LLM 에이전트 | gpt-4o-mini | `agents.py::router_agent` | 분류는 쉬운 일 → 싼 모델 |
| corpus 검색 | 코드(검색) | 임베딩+BM25 | `vectorstore.py::search` | 진짜 하이브리드(§4) |
| 재무 결합 | 코드(API) | — | `services/financials.py` | DART 정형수치 = 정확 라인아이템 1급 |
| 거시 결합 | 코드(API) | — | `services/macro.py`+`data/ecos.py` | macro_relevant일 때만, 병렬 |
| writer(QA) | LLM 에이전트 | gpt-5.1 | `agents.py::qa_agent` | 답 품질이 핵심 → 상위 모델 |
| summary | LLM 에이전트 | gpt-4o-mini | `agents.py::summary_agent` | 서술 요약(실시간 RAG, §5) |
| verifier | LLM 에이전트 | o4-mini | `agents.py::verifier_agent` | 추론형, 샘플링+임계값 |

### 2-3. 병렬(asyncio)이 실제로 어떻게
- corpus 검색·재무·거시는 **서로 독립** → `asyncio.gather`로 동시 실행. 가장 느린 하나만 기다림.
- **부분 실패 graceful**: 한 소스가 예외여도 `gather(return_exceptions=True)`로 나머지 근거로 진행.
- Logfire 콘솔에서 실제 동시 실행이 타임라인으로 확인됨(§7).

## 3. 에이전트 영역 — 어떻게 이뤄지고 활용되나 (핵심 ①)

### 3-1. 관용구: "모듈 레벨 1회 정의 + retrieve-then-read"
```python
# agents.py — 4개 에이전트를 모듈 로드 시 1회 생성(재사용)
qa_agent = Agent("openai:gpt-5.1", output_type=QAResult, instructions="근거 안에서만 답…")

# chat.py — 검색은 코드가 끝내고(retrieve), 근거를 프롬프트로 넣어 읽게 함(read)
evidence = format_citations(citations)            # 코드가 검색·정렬·결합
qa = (await qa_agent.run(f"[질문]…[근거]\n{evidence}")).output   # 에이전트는 작성만
```
- **왜 이 방식인가**: 에이전트에 "검색 툴"을 쥐여주면 (a)환각 (b)비용↑ (c)비결정성이 생긴다. 검색을 코드가 결정적으로 끝내면 **근거가 고정**돼 재현 가능하고 싸다. (실무 정확성-우선 RAG의 표준)

### 3-2. `output_type`의 가치 — 검증 + 자동 재시도
- `Agent(output_type=QAResult)`면 LLM 출력이 **QAResult 스키마로 검증**되고, **틀리면 PydanticAI가 자동 재시도**한다. 즉 "JSON 깨짐/필드 누락"을 프레임워크가 막는다. 기존엔 `output_pydantic` + 수동 `_as_pydantic` 추출이었다.

### 3-3. provenance(출처) 고정 — 환각 차단
- 에이전트가 citations를 **지어내지 못하게**, 응답의 출처는 **코드가 검색한 실제 근거**(`citations[:5]`)로 고정한다. (기존 `_reconcile`과 같은 목적; 재구축에선 아예 에이전트 인용을 안 믿고 검색 근거로 대체)

### 3-4. verifier — 샘플링 + 임계값
- 매 턴 검증은 비싸다 → **질문 해시로 20%만** 검증(`_should_verify`).
- verifier는 `grounded_score`(0~1)만 잘 매기고, **verdict(pass/partial/fail)는 코드가 임계값(0.7/0.4)으로 확정** → 모델의 라벨 변동을 제거(결정적).

### 3-5. 모델 티어링 (왜 모델이 다른가)
- 쉬운 일(분류·요약·문맥생성)=**gpt-4o-mini**(싸다), 답 작성=**gpt-5.1**(품질), 검증=**o4-mini**(추론형). `.env`로 조정.
- 비용 대부분은 writer(gpt-5.1)에 몰린다(Logfire로 확인 가능).

## 4. 청킹 — 어떻게 이뤄지고 활용되나 (핵심 ②)

### 4-1. 표-인식 파싱 (가장 큰 품질 레버)
- DART `document.xml`(ZIP→raw XML, **태그 보존**) → BeautifulSoup(lxml) 순회.
- `<TABLE>` → **Markdown 표**(행·열·`COLSPAN` 패딩 보존), `<P>` → 본문, `<TITLE>/<SECTION-*>` → 섹션 경로.
- 표 셀 4종(TD/TH/TE/TU) 모두 셀 처리, 자간 라벨("매 출 액"→"매출액") 경계검사 정규화.
- **기존과의 결정적 차이**: 기존은 모든 태그를 공백으로 치환 → **표가 plaintext로 뭉개져 행·열 소실**. 재구축은 `| 매출액 | 300,870,903 | 258,935,494 |` 구조를 보존 → 표 질문·정확 수치가 살아남음.

### 4-2. 청킹 + Contextual 주입
```
[삼성전자 · 사업보고서(2024.12) · II.사업의 내용 > 1.사업의 개요 · 본문]   ← Contextual 문맥줄(결정적)
당사는 본사를 거점으로 한국과 DX 부문 … DRAM, NAND Flash …                 ← raw_text
```
- 본문: 섹션 유지 + 슬라이딩 윈도우(800/120). 표: 통째 1청크, 크면 **헤더 반복하며 행 분할**.
- **임베딩 대상 = 문맥줄 + 원문**, 인용용 `raw_text`는 따로 보관.
- **Contextual의 효과**(Anthropic): 고아 청크("매출 3% 증가")에 "[삼성·2024사업보고서·매출]" 문맥을 붙여 임베딩 → 검색이 정확히 매칭. 회사별 컬렉션 분리 + `rcept_dt` 메타필터가 기업·기간 혼동을 추가 차단.
- 메타: `corp_code·rcept_no·report_nm·rcept_dt·section_title·kind·order` → 필터·출처추적.

### 4-3. 어디서 활용되나
- 적재: `corpus_<corp_code>` 컬렉션(cosine). 삼성 23,444 + 현대 43,579 = **67,023청크**.
- 검색 시 Contextual이 임베딩에 녹아 corpus 검색 품질을 끌어올림 → 최종 답 근거 품질↑.

## 5. 요약 — 어떻게 이뤄지고 활용되나 (핵심 ③)

### 5-1. 현재 구현: 실시간 RAG 요약
- "사업 내용 요약" → router=summary → corpus에서 **본문(text) 청크 우선 검색**(`summary_top_k=8`, kind=text 필터) → summary_agent가 그 근거로 **그 자리에서** 서술 요약.
- 장점: 단순·항상 최신. 단점: **매 턴 재검색+재요약**(느리고 비쌈), 품질이 그때 검색이 집은 청크에 좌우.

### 5-2. 원안(기존 코드가 가졌던) 사전요약 트랙 — 미구현(개선점)
- **빌드 시점에** 각 공시의 섹션을 싼 모델로 미리 요약 → 별도 `summary_<corp>` 컬렉션에 저장.
- 질의 시엔 **완성된 요약 조각을 빠르게 꺼내기**만 → 질의 비용↓·속도↑·품질↑(섹션 전체를 보고 1회 정성껏 요약).
- 실무 표준(AlphaSense Smart Summary, LlamaIndex Document Summary Index). **2-컬렉션 설계**(corpus=정확 사실 / summary=개요)를 완성하는 부분. → §6 개선점.

## 6. 실무(AlphaSense·Hebbia 등)와의 차이 + 추후 개선점
| 영역 | 실무 production | 본 프로젝트(현재) | 추후 개선 |
|---|---|---|---|
| 파싱 | 구조보존 + **XBRL 정형화** + 멀티모달(차트 비전) | 표-인식(Markdown)✓, XBRL은 DART 정형 API로 일부 | XBRL 본격 정형화, 차트/이미지 비전 |
| 청킹 | 표-인식 + 메타 + Contextual | ✓ (결정적 Contextual) | **LLM Contextual**(선택적, 청크별 상황문장) |
| 검색 | 하이브리드 + **전용 reranker(cross-encoder)** | 진짜 하이브리드(벡터∪BM25 RRF)✓ + dedup/recency 휴리스틱 | cross-encoder 리랭커 모델 |
| 쿼리 | **에이전트 쿼리 분해**(복합 질문 다단계) | 단일 라우팅 + 쿼리 정제 | 복합질문 분해(시나리오 D) |
| 요약 | Smart Summary(precompute) + 토픽 택소노미·감성 | 실시간 RAG 요약 | **사전요약 트랙**(§5-2), 토픽 태깅·변화탐지(takeaway) |
| 규모 | 500M+ 문서, 준실시간 | 2개사 32건(정기보고서) | 기업·공시유형 확장 |
| 운영 | 관찰성·테스트·배포 표준 | Logfire 콘솔✓ | Logfire 클라우드, pytest, Dockerfile |

## 7. X-Trace-Id 端-to-端 추적 — 구현 완료 ✅
### 7-1. 동작
- finance_v2(Spring) → FastAPI 호출 시 헤더 `X-Trace-Id` 전달 → `routes.py`가 **응답 헤더로 echo**(요청-응답 상관) **+ 루트 span에 바인딩**.
- `routes.py`가 챗 처리 전체를 `request_span("chat", trace_id=x_trace_id, room_id, corp_code)`로 감싼다(`app/observability.py`). 그 아래 모든 AI 내부 호출이 자식 span으로 중첩:
```
POST /api/v1/chat
```
