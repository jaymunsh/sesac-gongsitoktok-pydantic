한 줄 요약 — 한국 전자공시(DART) 원문을 표 구조까지 보존해 적재하고, 질문하면 근거(출처)와 함께 답하고 보관·조회하는 PydanticAI 기반 RAG 챗봇. 정확 수치는 RAG가 아닌 DART 정형 API로, 모든 답에 출처 추적(provenance)과 정확도 점수가 붙는다.

1-2. 용어 한눈에 (Glossary)

이 문서에 자주 나오는 용어. 모르는 단어가 보이면 여기로.

용어쉬운 뜻
RAG (검색증강생성)질문에 맞는 근거를 검색해서 그 근거로 LLM이 답하는 방식. 환각↓·근거 기반.
임베딩 / 벡터 검색글을 숫자 벡터로 바꿔 '뜻'이 비슷한 것을 찾기. 개념·서술 질문에 강함.
BM25단어가 글자 그대로 얼마나 잘 맞는지로 순위를 매기는 고전 키워드 검색 알고리즘(검색엔진 표준). 티커·정확 수치·고유명사에 강함.
하이브리드 검색벡터(뜻) + BM25(단어)를 함께 써서 둘의 강점을 결합. 공시는 개념+정확수치 둘 다 필요해서 씀.
RRF (순위 융합)여러 검색의 순위를 합쳐 하나로 정렬하는 표준 기법(1/(60+순위) 합산). 점수 단위가 달라도 공정하게 섞임.
리랭킹(Re-ranking)검색 후보를 더 정밀하게 다시 정렬(여기선 중복제거·최신우선 휴리스틱).
Contextual Retrieval청크 앞에 출처 문맥 한 줄("[삼성 2024 사업보고서 매출]")을 붙여 임베딩 → 검색 정밀도↑(Anthropic 제안).
청크(Chunk)긴 문서를 검색·요약하기 좋게 자른 작은 조각(색인 카드).
메타데이터청크에 붙는 꼬리표(회사·기간·섹션·종류 등) — 필터·출처추적·랭킹에 사용.
provenance (근거추적)답의 각 주장이 어느 원문에서 왔는지 되짚기. 환각 억제·감사 → 금융권 필수.
정형재무 / XBRL매출·영업이익처럼 표준 태그로 기계가 읽는 재무 수치. 본 프로젝트는 DART API로 직접 가져옴(RAG 아님).
retrieve-then-read검색은 코드가 끝내고 그 근거를 LLM 프롬프트에 넣어 읽게 하는 패턴(환각·비용·비결정성↓).
접수번호(rcept_no)DART 공시 1건의 14자리 고유 식별자(앞 8자리=접수일). 출처·원문 링크의 기준.
코사인 유사도두 벡터가 얼마나 같은 방향인지(1=동일, 0=무관). 임베딩 검색의 거리 척도.
groundedScore (정확도)답이 근거에 얼마나 충실한지(0~1). 프론트 "정확도 %"로 표시(verifier 산출).
verdict (판정)검증 결과 pass/partial/fail. groundedScore를 임계값(0.7/0.4)으로 코드가 확정.

3실무는 어떻게 / 우리는 어떻게 구현했나

현업 공시분석(AlphaSense·Hebbia)은 "그냥 텍스트 청킹+벡터검색"이 아니다. 7단계 production 파이프라인으로 돌아가며, 본 프로젝트는 그 축소·국내(DART)·대화형 버전을 구현했다.

4-3. Contextual 문맥줄 — 검색 정확도의 핵심

문제 고아 청크("매출 3% 증가")는 어느 회사·기간·섹션인지 임베딩에 안 담겨 검색이 어긋남. 해법(Anthropic Contextual Retrieval) 청크 앞에 문맥 한 줄을 붙여 임베딩.
형식  [<회사> · <공시명> · <섹션경로> · (표 제목) · <종류>]
예    [삼성전자 · 사업보고서(2024.12) · II. 사업의 내용 > 1. 사업의 개요 · 본문]
      [삼성전자 · 사업보고서(2024.12) · (첨부)연결재무제표 · 연결손익계산서 · 표]
  • 결정적(무료): 메타로 템플릿 생성 → LLM 비용 0 (contextual.build_context_line).
  • DART는 섹션 계층(I~XII)이 명확해 section_title이 풍부하고, 표 캡션까지 문맥에 넣어 일반 문서보다 유리.

4-4. 메타 활용처

  • 컬렉션 분리(corpus_<corp_code>) + rcept_dt 필터 → 기업·기간 혼동을 구조적으로 차단.
  • kind → 요약 트랙은 text 청크 우선(빈약한 수치 표에 안 끌려가게).
  • rcept_no/report_nm/rcept_dt → 출처 카드(sources[])·DART 원문 링크(dartUrl) 생성.

5PydanticAI란 & 채택 이유 (vs LangGraph) 강조

5-1. PydanticAI란

Pydantic 팀의 타입세이프 에이전트 프레임워크(V1, 2025). 핵심:

  • 구조화 출력 1급 — Agent(output_type=Model) → LLM 결과를 Pydantic으로 검증 + 실패 시 자동 재시도.
  • deps 주입 — 벡터스토어·설정을 타입 안전하게 주입.
  • 경량·Pydantic-native — 기존 결과 스키마(RouterResult/QAResult)를 그대로 output_type으로 재사용.

5-2. 프레임워크 비교

프레임워크한 줄우리 적합도
LangChain부품 상자(통합·RAG)부품엔 좋으나 무거움
LangGraph순서도를 코드로(상태 그래프)흐름이 매우 복잡하면 ◎, 우리 규모엔 과함
PydanticAI타입세이프 에이전트(구조화 출력)◎ Pydantic-native·경량·최소코드
CrewAI(기존)역할극 팀단일 래퍼로 전락 → 가치 0

5-3. 왜 PydanticAI인가 (LangGraph 대비)

우리 오케스트레이션(라우터→검색→작성→검증 + 병렬 결합)은 분기·병렬이 평범한 파이썬 (if/else, asyncio.gather)으로 충분히 표현된다. LangGraph의 상태 그래프(노드·엣지 선언)는 이 정도 흐름엔 추상화 과잉. 반면 매 단계 진짜 원하는 건 "LLM 출력을 정해진 스키마로 안전하게 받기" — 이게 PydanticAI의 1급 기능. 그래서 흐름은 코드로, 각 호출은 PydanticAI로가 최소 코드·최대 타입안정의 조합. 기존이 Pydantic 결과를 쓰고 있어 교체 비용도 가장 적다.

더 복잡한 흐름(다단계 분기·롤백·휴먼인더루프)이 필요해지면 PydanticAI의 pydantic-graph로 확장 가능.

  1. ① 원문 수집 — 태그 보존 raw XML
    dart.fetch_document_xml(rcept_no)가 OpenDART document.xml(ZIP)을 받아 압축 해제 후 태그를 그대로 남긴 raw XML로 반환한다. 기존 코드는 여기서 모든 태그를 공백으로 치환해 평문으로 만들어 표가 소실됐는데, 재구축은 "표를 표로 살릴지"의 판단을 파서로 미룬다. 인코딩(utf-8/cp949/euc-kr)도 여기서 흡수.
  2. ② 표-인식 파싱 → Block
    parser.parse_document이 BeautifulSoup(lxml)로 문서 트리를 순회한다. <TABLE>은 행(<TR>)·셀(TD/TH/TE/TU 4종)을 읽어 Markdown 표로 변환하고 COLSPAN은 빈 칸으로 패딩해 열 정렬을 유지한다. <P>는 본문, <TITLE>/<SECTION-*>는 섹션 경로(I. → 1. → 가.)로 추적. DART가 자간으로 띄운 "매 출 액"은 앞뒤 경계를 검사하는 정규식으로 "매출액"으로만 안전하게 붙인다(BM25 매칭↑, "가전 및 모바일" 같은 오병합 방지). 산출물은 Block(kind=text|table, text, section_path, table_title) 리스트.
  3. ③ 청킹 → Chunk
    chunker.chunk_blocks. 본문은 섹션을 유지한 채 슬라이딩 윈도우(800자/겹침 120)로 자르고, 표는 통째로 1청크. 표가 table_max_chars(2400)보다 크면 헤더 행을 매 조각에 반복하며 행 단위로 나눠 각 조각이 열 의미를 잃지 않게 한다. (개발 중 거대 "가짜 헤더"가 반복돼 청크가 폭증한 버그가 있었고 → 헤더가 비정상적으로 크면 반복을 끄고 _hard_wrap으로 강제 분할하도록 수정 — §12-2 개발 일지)
  4. ④ Contextual 주입 (결정적·무료)
    contextual.build_context_line이 메타로 문맥 한 줄 [회사 · 공시명 · 섹션 · (표 제목) · 종류]을 만들어 청크 앞에 붙인다. 임베딩 대상 text = 문맥줄 + 원문, 화면 인용용 raw_text는 문맥줄 없이 따로 보관. 고아 청크("매출 3% 증가")가 어느 회사·기간·섹션인지 임베딩에 녹아 검색 정밀도가 오른다. LLM 미사용 → 비용 0.
  5. ⑤ 임베딩 & ⑥ 색인
    embedder가 text-embedding-3-small로 256개씩 배치 임베딩하고, vectorstore.index_chunks가 회사별 컬렉션 corpus_<corp>(코사인)에 ChunkMeta와 함께 저장. 이미 적재된 공시는 has_disclosure로 건너뛴다(재실행 안전).

  6. ⑥ provenance 고정 — 응답의 출처는 에이전트가 고른 게 아니라 코드가 검색한 실제 근거(citations[:5])로 고정한다(인용 환각 차단).
  7. ⑦ 검증 — _should_verify(verify_sample_rate=1.0이면 매 턴)면 verifier(o4-mini)가 답이 근거에 충실한지 grounded_score(0~1)를 매기고, verdict(pass/partial/fail)는 코드가 임계값(0.7/0.4)으로 확정(모델 라벨 변동 제거).
  8. ⑧ 응답 변환·보관 — contract.to_v2가 내부 결과를 v2.0 ChatV2Response(answerText·sourceContent·sources·macroSnapshot·verification)로 번역하고, 근거 있는 답이면 storage.save_chat으로 SQLite에 보관(→ 목록/상세 조회).

6-4. End-to-End 워크스루 — "삼성전자 영업이익 알려줘"

한 질문이 들어와서 답이 나가기까지 실제 값으로 따라가 본다.

  1. 요청 — React→Spring→FastAPI로 {roomId, companyContext:{corpCode:"00126380", corpName:"삼성전자"}, messages:[{role:"user", content:"삼성전자 영업이익 알려줘"}]} 도착. X-Trace-Id가 있으면 Logfire 루트 span에 바인딩.
  2. 라우터(gpt-4o-mini) — → RouterResult(intent=qa, financial_relevant=true, macro_relevant=false, search_query="영업이익", out_of_scope=false). "영업이익"이라 재무 플래그 ON.
  3. 병렬 검색·결합 — asyncio.gather로 동시에: ⓐ corpus에서 "영업이익" 하이브리드 검색(손익계산서 등 근거), ⓑ 재무 결합이 DART fnlttSinglAcnt(00126380) 호출 → 연결 영업이익 행을 score=1.0 citation으로 만들어 맨 앞에 배치. quote 예: "영업이익: 제 57 기 43,601,051,000,000 / 제 56 기 32,725,961,000,000 (단위 원, 연결, 2025 사업보고서 기준)", rcept_no=실제 접수번호.
  4. 작성(writer gpt-5.1) — 재무 citation을 1급 근거로 받아 페르소나·콤마표기·근거 기수로: "삼성전자 영업이익은 제 57 기 43,601,051,000,000원, 제 56 기 32,725,961,000,000원입니다."
  5. provenance 고정 + 검증 — 출처는 코드의 실제 근거(citations[:5])로 고정. verifier(o4-mini)가 grounded_score≈1.0 → 임계값으로 verdict=pass.
  6. 응답·보관 — contract.to_v2가 answerText+sources[](rceptNo·dartUrl 포함)+ verification{verdict:"pass", groundedScore:1.0}로 변환, SQLite 보관. 프론트는 "정확도 100%"와 출처 카드(+DART 링크)를 표시.

7에이전트 영역 상세 핵심

7-1. 관용구 — 모듈 레벨 1회 정의 + retrieve-then-read

# agents/agents.py — 모듈 로드 시 1회 생성(재사용)
qa_agent = Agent("openai:gpt-5.1", output_type=QAResult, instructions=_PERSONA + "근거 안에서만 답…")

# services/chat.py — 검색은 코드가 끝내고(retrieve), 근거를 프롬프트로 넣어 읽게(read)
evidence = format_citations(citations)
qa = (await qa_agent.run(f"[질문]…[근거]\n{evidence}")).output   # 에이전트는 작성만
왜 — 에이전트에 검색 툴을 주면 (a)환각 (b)비용↑ (c)비결정성. 검색을 코드가 결정적으로 끝내면 근거가 고정돼 재현 가능·저렴(실무 정확성-우선 RAG의 표준).
7-2. output_type
Agent(output_type=QAResult)면 출력이 스키마로 검증되고 틀리면 자동 재시도. JSON 깨짐/필드 누락을 프레임워크가 막음.
7-3. provenance 고정
에이전트가 인용을 못 지어내게, 출처는 코드가 검색한 실제 근거(citations[:5])로 고정. 재무 정형수치가 앞에 배치돼 항상 포함.
7-4. verifier 샘플링+임계값
검증 빈도는 verify_sample_rate(현재 1.0). verifier는 grounded_score만 매기고 verdict는 코드가 임계값(0.7/0.4)으로 확정(결정적).
7-5. 공통 페르소나
4개 에이전트가 _PERSONA(존댓말·차분·서론 금지·사실 중심) 공유 → 모델이 달라도 말투 일정. 수치는 출처 콤마 표기 그대로, 기수는 근거 명칭 그대로.

8-3. 원안(미구현) — 사전요약 트랙
아키텍처 원안은 빌드 시점에 각 섹션을 싼 모델로 미리 요약해 별도 컬렉션 summary_<corp>에 저장하고, 질의 시엔 완성된 요약을 꺼내쓰기만 하는 것(요약 품질↑·질의 비용↓). 본 재구축은 아직 실시간 RAG로 처리 — 남은 핵심 개선점(§15).

9과제형 보관/조회 + v2.0 계약 연동

9-1. 과제형(RFP 1급): 요약→근거 QA→보관→조회

  • POST /api/v1/chat — 근거 있는 답을 SQLite(analyses)에 자동 보관.
  • GET /api/analyses — 목록(마이페이지 카드). GET /api/analyses/{id} — 상세(근거·검증).

9-2. v2.0 계약 (백엔드 finance_v2 드롭인 호환)

내부 스키마와 분리된 camelCase 와이어 계약을 contract.py 어댑터로 변환 → 백엔드 코드 수정 없이 연동.

요청  ChatV2Request : { roomId, userSeq, companyContext:{corpCode,corpName}, messages:[{role,content}] }
응답  ChatV2Response: { roomId, intent, answerText, sourceContent, macroSnapshot,
                       sources:[{rceptNo,reportNm,rceptDt,sectionTitle,quote,score,dartUrl}],
                       outOfScope, detectedCompany, needsClarification,
                       verification:{verdict,groundedScore}, error }
verification.groundedScore(0~1) = 답변 1건의 최종 정확도(프론트 "정확도 %"). sources[].score = 출처별 검색 관련도(0~1 정규화). dartUrl = DART 원문 링크.

9-3. X-Trace-Id 端-to-端 추적

백엔드가 보낸 X-Trace-Id를 응답 헤더로 echo + Logfire 루트 span에 바인딩. 그 아래 AI 내부 호출(router→검색→writer→verifier)이 자식 span으로 묶여, 백엔드 trace_id 하나로 AI 추론 과정까지 추적(금융권 감사가능성). 관찰성 off면 no-op.

11기존(CrewAI)에서 바꾼 결정적·합리적 이유

핵심 — 오케스트레이션(흐름)은 두 버전 모두 services/chat.py(우리 코드)에 있고 프레임워크 독립적. 즉 "기존도 이미 아키텍처화돼 있었다." 진짜 바뀐 핵심 3가지:
  1. 인제스트 — 표 plaintext 뭉갬 → 표-인식 보존 + Contextual (가장 큰 품질 레버)
  2. 검색 — 벡터+키워드폴백 → 진짜 하이브리드(벡터∪전체BM25 RRF) + dedup/최신우선
  3. 프레임워크 — 무거운 CrewAI 단일 래퍼 → 경량 PydanticAI

12-2. 개발 일지 — 잡은 버그와 교훈

코드가 지금 모양인 이유는 대개 이 버그들에서 왔다. 증상 → 원인 → 수정.

증상원인수정 / 교훈
청크가 폭증(삼성 1건 11.7M자, 임베딩 한계 초과)일부 표의 "헤더"가 1.8만자 거대 셀인데, 그걸 매 조각에 반복헤더가 비정상이면 반복 끄고 _hard_wrap으로 강제 분할. 표 분할에 안전장치 필수
요약이 일반지식 환각, 출처가 답 문장과 동일summary 에이전트가 근거 대신 자기 문장을 citations로 생성(순환참조)provenance를 코드의 실제 검색 근거(citations[:5])로 고정. 에이전트에 출처를 맡기지 말 것
"현대 매출" 정확수치가 빠짐(회귀)재무 citation을 corpus 뒤에 붙여 citations[:5]에서 잘림재무 정형수치를 앞에 배치. 1급 근거는 순서가 중요
"지역별 매출"이 엉뚱한 주주현황을 잡음RRF 가중 0.6/0.4라 벡터 후보 5개가 BM25 1위보다 높아 top-5가 사실상 순수 벡터동등 가중(0.5)으로 1:1 교차. 융합 가중이 한쪽을 묻으면 하이브리드가 아님
"삼성랑 SK 비교"가 out_of_scope로 안 걸림방 회사(삼성)가 같이 언급돼 in-scope로 오판. 기존 골든은 순수 타사라 못 잡음라우터에 비교 질문 규칙 추가. 행동 평가(eval)가 이 버그를 잡음
답마다 말투·도입부가 제각각, 기수(제56/57기) 오기답 주체 4개가 페르소나 미공유 + 재무 근거에 기수 명칭 없어 모델이 추측공통 _PERSONA + 재무 quote에 실제 기수(thstrm_nm) 포함. 일관성은 공유 규칙 + 근거 명시로
verifier verdict가 런마다 pass↔fail 변동모델이 verdict 라벨을 직접 매겨 비결정적grounded_score만 받고 verdict는 코드가 임계값(0.7/0.4)으로 확정. 판정은 결정적으로
교훈 요약 — ①에이전트엔 "작성"만 맡기고 출처·판정은 코드가 고정 ②융합·분할엔 안전장치 ③일관성은 공유 페르소나+근거 명시 ④좋은 eval이 진짜 버그를 잡는다.

14시연 강조 포인트

  1. 표파싱 before/after — "지역별/부문별 매출"에서 표가 plaintext로 뭉개지지 않고 행·열 보존됨을 대비.
  2. 요약 트랙 — "사업 내용 요약" → 본문 청크 기반 서술(반도체·메모리·DX·DS·하만).
  3. 정확수치=재무결합 — "영업이익 얼마?" → DART 정형 API로 43,601,051,000,000원 정확 제시(+접수번호·DART 링크).
  4. 거시결합 — "요즘 환율·금리 상황에서 실적 어때?" → macroSnapshot(환율·기준금리·국고채·KOSPI).
  5. 정확도·provenance — 모든 답에 근거 충실도 % + 출처 카드 + DART 원문 링크.
  6. 평가 수치 — 검색 must 11/11 hit@5(100%)·MRR 0.923, 회귀 골든 14/14.
  7. API 절약 로직 — 모델 티어링·retrieve-then-read·정형API·캐시(§13)로 "왜 싸고 정확한지".
  8. X-Trace-Id + Logfire 콘솔 — 한 요청의 내부 추론(router→검색→writer→verifier) 타임라인 시연.
  9. 스코프 가드 — 방 회사가 아닌/비교 질문 차단(out_of_scope) → 객관성·범위 통제.

15-1. 확장 시 주의 — 정형재무 "라이브 조회"
정형재무는 런타임에 DART API로 그때그때 조회(캐시 없음)한다. 정확성·신선도가 핵심인 데이터라 의도된 선택이며, 현재 규모(2개사·무료 API·데모)엔 최적. 단 규모가 커지면: ①중복 호출(같은 질문 반복 시 동일 DART 호출 — 거시는 캐시하나 재무는 미캐시, 비대칭) ②OpenDART 일 1만건 레이트리밋 ③DART 장애 시 재무 답 저하(현재 graceful 완화). → 개선책: 거시와 동일하게 rcept_no 기준 또는 짧은 TTL 캐시로 "신선도 유지 + 중복 제거". 확정 보고서 수치는 불변이라 캐시 안전.
