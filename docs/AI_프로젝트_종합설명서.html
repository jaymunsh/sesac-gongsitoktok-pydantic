레포 gongsitoktok-pydantic · 작성 2026-06-23 · 대상: 처음 보는 사람도 바로 파악 + 시연/발표용
한 줄 요약 — 한국 전자공시(DART) 원문을 표 구조까지 보존해 적재하고, 질문하면 근거(출처)와 함께 답하고 보관·조회하는 PydanticAI 기반 RAG 챗봇. 정확 수치는 RAG가 아닌 DART 정형 API로, 모든 답에 출처 추적(provenance)과 정확도 점수가 붙는다.
읽는 순서 가이드 — 처음 보는 분은 §1(특히 용어 한눈에)~§5, 개발자는 §6(파이프라인)~§12(개발 일지), 발표·시연은 §14(강조 포인트)부터 보면 빠릅니다.

1한눈에 — 무엇을 하는 시스템인가

비유: 회사의 공시 문서를 잘게 잘라 "색인 카드"로 만들어 도서관에 꽂아두고, 질문하면 관련 카드를 찾아 그 근거 안에서만 답하고, 그 답을 보관해 나중에 목록·상세로 조회하는 시스템.

  1. 데이터 소스 (무료 API) — OpenDART에서 공시 원문(사업/분기보고서)과 정형 재무(fnlttSinglAcnt)를, 한국은행 ECOS에서 거시지표(환율·기준금리·국고채·KOSPI)를 가져온다. OpenAI는 임베딩·LLM에만 쓴다.

  4. 서빙·연동 평면 — React 프론트(gongsitoktok-react) ↔ Spring 백엔드(gongsitoktok-spring) ↔ 본 FastAPI가 v2.0 계약으로 통신한다. AI는 추론만(stateless) 하고, 답의 보관·마이페이지 조회는 백엔드가 담당한다(§9).

1-2. 용어 한눈에 (Glossary)

이 문서에 자주 나오는 용어. 모르는 단어가 보이면 여기로.

용어쉬운 뜻
RAG (검색증강생성)질문에 맞는 근거를 검색해서 그 근거로 LLM이 답하는 방식. 환각↓·근거 기반.
임베딩 / 벡터 검색글을 숫자 벡터로 바꿔 '뜻'이 비슷한 것을 찾기. 개념·서술 질문에 강함.
BM25단어가 글자 그대로 얼마나 잘 맞는지로 순위를 매기는 고전 키워드 검색 알고리즘(검색엔진 표준). 티커·정확 수치·고유명사에 강함.
하이브리드 검색벡터(뜻) + BM25(단어)를 함께 써서 둘의 강점을 결합. 공시는 개념+정확수치 둘 다 필요해서 씀.
RRF (순위 융합)여러 검색의 순위를 합쳐 하나로 정렬하는 표준 기법(1/(60+순위) 합산). 점수 단위가 달라도 공정하게 섞임.
리랭킹(Re-ranking)검색 후보를 더 정밀하게 다시 정렬(여기선 중복제거·최신우선 휴리스틱).
Contextual Retrieval청크 앞에 출처 문맥 한 줄("[삼성 2024 사업보고서 매출]")을 붙여 임베딩 → 검색 정밀도↑(Anthropic 제안).
청크(Chunk)긴 문서를 검색·요약하기 좋게 자른 작은 조각(색인 카드).
메타데이터청크에 붙는 꼬리표(회사·기간·섹션·종류 등) — 필터·출처추적·랭킹에 사용.
provenance (출처추적)답의 각 문장·수치가 어느 공시·섹션에서 왔는지 끝까지 되짚는 것. "이 숫자 어디서 났어?"에 답할 수 있게 함 → 환각 억제·감사(금융권 필수). 본 프로젝트는 출처를 코드가 고정하고 화면에 출처 카드+DART 링크로 보여줌.
정형재무 / XBRL매출·영업이익처럼 표준 태그로 기계가 읽는 재무 수치. 본 프로젝트는 DART API로 직접 가져옴(RAG 아님).
retrieve-then-read검색은 코드가 끝내고 그 근거를 LLM 프롬프트에 넣어 읽게 하는 패턴(환각·비용·비결정성↓).
접수번호(rcept_no)DART 공시 1건의 14자리 고유 식별자(앞 8자리=접수일). 출처·원문 링크의 기준.
코사인 유사도두 벡터가 얼마나 같은 방향인지(1=동일, 0=무관). 임베딩 검색의 거리 척도.
groundedScore (정확도)답이 근거에 얼마나 충실한지(0~1). 프론트 "정확도 %"로 표시(verifier 산출).
verdict (판정)검증 결과 pass/partial/fail. groundedScore를 임계값(0.7/0.4)으로 코드가 확정.

시스템·데이터·평가 용어

용어쉬운 뜻
corpus (코퍼스)회사별 공시 원문 청크 저장소(corpus_<회사>). 정확 사실·QA용. (사전요약은 별도 summary_<회사>)
사전요약 (precompute summary)빌드때 섹션을 미리 요약해 summary_<회사>에 저장 → 요약 질문에 꺼내 씀(매번 안 만듦).
인제스트 (ingest)공시 원문을 파싱·청킹·임베딩해 적재하는 빌드 단계(1회, 큰 비용은 여기).
런타임 (runtime)질문이 들어와 답하는 실행 단계(질문당, 푼돈).
Chroma본 프로젝트가 쓰는 벡터 데이터베이스(임베딩 저장·검색).
라우터 (router)질문의 의도를 분류하고 검색쿼리·플래그·기간을 정하는 첫 에이전트(gpt-4o-mini).
intent (의도)질문 종류: qa(사실·수치) / summary(요약) / smalltalk(잡담) / out_of_scope(다른 회사).
eval (평가)시스템이 잘 작동하는지 자동 검증하는 테스트 묶음. 본 프로젝트는 검색·행동·회귀 3계층.
골든셋 (golden set)정답 기대값을 정해둔 회귀 테스트 케이스 모음(바뀌어도 안 깨지는지 확인).
hit@k / MRR검색 평가 지표 — hit@k=정답이 상위 k개 안에 있나, MRR=정답 순위의 역수 평균(1에 가까울수록 좋음).
DART / OpenDART금융감독원 전자공시시스템 / 그 무료 API(공시 원문·정형재무). fnlttSinglAcnt=주요계정 재무 API.
ECOS한국은행 경제통계 API(환율·기준금리·국고채·KOSPI 등 거시지표).
정기보고서사업보고서·반기보고서·분기보고서(DART 공시유형 A). 본 프로젝트의 적재 대상.
토큰 (token)LLM이 글을 처리하는 단위(대략 단어 조각). 비용·길이 계산 기준.
폴백 (fallback)주 경로가 안 되면 대체 경로로 처리(예: 사전요약 없으면 corpus RAG로).
v2.0 계약백엔드(Spring)와 합의한 요청/응답 규격(필드명·구조). 어댑터가 내부 스키마와 번역.

구현·기술 용어 (라이브러리·기법)

용어쉬운 뜻
asyncio / gather파이썬 비동기 동시 실행 도구. 검색·재무·거시를 동시에 돌려 가장 느린 하나만 기다림(병렬). gather=여러 작업을 한 번에 모아 실행.

output_type에이전트 출력을 정해진 스키마로 검증(+실패 시 자동 재시도)하는 PydanticAI 기능.

graceful (부분실패 처리)한 부분(예: 거시 결합)이 실패해도 나머지로 계속 진행해 답을 만든다.
TTL (time to live)캐시의 유효 시간. 지나면 새로 가져온다(예: 정형재무 캐시 개선안).
FastAPI / uvicorn파이썬 웹 API 프레임워크 / 그 API를 띄우는 서버.
BeautifulSoup / lxmlHTML·XML을 트리로 파싱하는 라이브러리(표-인식 파싱에 사용).
SQLite파일 하나로 동작하는 가벼운 데이터베이스(분석 보관·거시 캐시).
venv파이썬 가상환경 — 프로젝트별 의존성 격리.
COLSPAN표 셀이 여러 열에 걸침(병합). 파서가 빈 칸으로 패딩해 열 정렬을 유지.

3실무는 어떻게 / 우리는 어떻게 구현했나

4-3. Contextual 문맥줄 — 검색 정확도의 핵심

문제 고아 청크("매출 3% 증가")는 어느 회사·기간·섹션인지 임베딩에 안 담겨 검색이 어긋남. 해법(Anthropic Contextual Retrieval) 청크 앞에 문맥 한 줄을 붙여 임베딩.
형식  [<회사> · <공시명> · <섹션경로> · (표 제목) · <종류>]
예    [삼성전자 · 사업보고서(2024.12) · II. 사업의 내용 > 1. 사업의 개요 · 본문]
      [삼성전자 · 사업보고서(2024.12) · (첨부)연결재무제표 · 연결손익계산서 · 표]
  • 결정적(무료): 메타로 템플릿 생성 → LLM 비용 0 (contextual.build_context_line).
  • DART는 섹션 계층(I~XII)이 명확해 section_title이 풍부하고, 표 캡션까지 문맥에 넣어 일반 문서보다 유리.

4-4. 메타 활용처

  • 컬렉션 분리(corpus_<corp_code>) + rcept_dt 필터 → 기업·기간 혼동을 구조적으로 차단.
  • kind → 요약 트랙은 text 청크 우선(빈약한 수치 표에 안 끌려가게).
  • rcept_no/report_nm/rcept_dt → 출처 카드(sources[])·DART 원문 링크(dartUrl) 생성.

5PydanticAI란 & 채택 이유 (vs LangChain/LangGraph) 강조

5-0. 짧은 역사 — 왜 프레임워크가 여러 개인가

LLM 앱 프레임워크는 "무엇이 어려운가"가 바뀌며 진화했다. 흐름을 알면 PydanticAI의 자리가 보인다.

  1. LangChain (2022~) — LLM에 검색·도구·메모리를 붙이는 "부품 상자". RAG 붐을 이끌었지만, 추상화가 많아 "무거움·추상화 누수(원하는 대로 안 풀림)" 비판을 받았다.
  2. LangGraph (2024~) — LangChain 팀이 낸, 상태 그래프(노드·엣지)로 복잡·순환 흐름을 제어하는 도구. 에이전트가 빙빙 돌거나 분기·롤백·휴먼인더루프가 필요한 복잡한 워크플로에 강하다.
  3. 역할극 멀티에이전트 — CrewAI/AutoGen (2024~) — "역할 가진 에이전트들이 협업"하는 패러다임. 표현력은 좋지만 단순 작업엔 과하고 무겁다(우리 기존이 이걸 단일 래퍼로 썼던 케이스).
  4. PydanticAI (2024말~2025) — Pydantic(파이썬 검증 라이브러리 표준) 팀이 낸 타입세이프 에이전트. "에이전트 = 모델 + 구조화 출력(검증) + 도구/의존성"으로 단순화. 가볍고 타입 안전한 게 차별점.

5-1. PydanticAI란 (상세)

Pydantic 팀의 타입세이프 에이전트 프레임워크(V1, 2025). FastAPI가 웹에서 한 일(타입·검증 1급)을 LLM 에이전트에서 하려는 도구. 핵심 기능:

  • 구조화 출력 1급 — Agent(output_type=Model) → LLM 출력을 Pydantic 모델로 검증하고, 스키마에 안 맞으면 자동 재시도. (우리의 RouterResult/QAResult가 항상 올바른 모양으로 옴)
  • deps(의존성 주입) — 벡터스토어·설정 등을 타입 안전하게 주입(RunContext).
  • instructions / tools / model-agnostic — 시스템 지시·도구 함수·여러 provider(OpenAI/Anthropic 등)를 동일 API로.
  • Logfire 관찰성 1급 — 같은 팀 제품이라 trace가 매끄럽게 연동(§9-3).
  • pydantic-graph — 흐름이 정말 복잡해지면 그래프로 확장 가능(우리는 미사용).

5-3. 왜 PydanticAI인가 (LangGraph 대비)

우리 오케스트레이션(라우터→검색→작성→검증 + 병렬 결합)은 분기·병렬이 평범한 파이썬 (if/else, asyncio.gather)으로 충분히 표현된다. LangGraph의 상태 그래프(노드·엣지 선언)는 이 정도 흐름엔 추상화 과잉. 반면 매 단계 진짜 원하는 건 "LLM 출력을 정해진 스키마로 안전하게 받기" — 이게 PydanticAI의 1급 기능. 그래서 흐름은 코드로, 각 호출은 PydanticAI로가 최소 코드·최대 타입안정의 조합. 기존이 Pydantic 결과를 쓰고 있어 교체 비용도 가장 적다.

더 복잡한 흐름(다단계 분기·롤백·휴먼인더루프)이 필요해지면 PydanticAI의 pydantic-graph로 확장 가능.

5-4. 프레임워크를 쓰는 명확한 이점 (Spring 비유) — 왜 체감이 "드라마틱"하진 않은가

먼저 솔직히 — Spring을 써도 앱이 "하는 일"은 안 바뀐다. Spring은 DI·트랜잭션·GC 연동·보일러플레이트 제거로 구조와 안전성을 준다. PydanticAI도 똑같다. 그래서 "기능이 확 달라진" 체감이 없는 게 정상 — 대신 코드가 안전하고 가벼워지고, 실수를 프레임워크가 막아준다. 진짜 품질 체감은 인제스트(표파싱·Contextual)·검색(하이브리드)에서 온다(§6). 프레임워크는 "그 로직을 깔끔히 받쳐주는 토대".

  1. ① 원문 수집 — 태그 보존 raw XML
    dart.fetch_document_xml(rcept_no)가 OpenDART document.xml(ZIP)을 받아 압축 해제 후 태그를 그대로 남긴 raw XML로 반환한다. 기존 코드는 여기서 모든 태그를 공백으로 치환해 평문으로 만들어 표가 소실됐는데, 재구축은 "표를 표로 살릴지"의 판단을 파서로 미룬다. 인코딩(utf-8/cp949/euc-kr)도 여기서 흡수.
  2. ② 표-인식 파싱 → Block
    parser.parse_document이 BeautifulSoup(lxml)로 문서 트리를 순회한다. <TABLE>은 행(<TR>)·셀(TD/TH/TE/TU 4종)을 읽어 Markdown 표로 변환하고 COLSPAN은 빈 칸으로 패딩해 열 정렬을 유지한다. <P>는 본문, <TITLE>/<SECTION-*>는 섹션 경로(I. → 1. → 가.)로 추적. DART가 자간으로 띄운 "매 출 액"은 앞뒤 경계를 검사하는 정규식으로 "매출액"으로만 안전하게 붙인다(BM25 매칭↑, "가전 및 모바일" 같은 오병합 방지). 산출물은 Block(kind=text|table, text, section_path, table_title) 리스트.
  3. ③ 청킹 → Chunk
    chunker.chunk_blocks. 본문은 섹션을 유지한 채 슬라이딩 윈도우(800자/겹침 120)로 자르고, 표는 통째로 1청크. 표가 table_max_chars(2400)보다 크면 헤더 행을 매 조각에 반복하며 행 단위로 나눠 각 조각이 열 의미를 잃지 않게 한다. (개발 중 거대 "가짜 헤더"가 반복돼 청크가 폭증한 버그가 있었고 → 헤더가 비정상적으로 크면 반복을 끄고 _hard_wrap으로 강제 분할하도록 수정 — §12-2 개발 일지)
  4. ④ Contextual 주입 (결정적·무료)
    contextual.build_context_line이 메타로 문맥 한 줄 [회사 · 공시명 · 섹션 · (표 제목) · 종류]을 만들어 청크 앞에 붙인다. 임베딩 대상 text = 문맥줄 + 원문, 화면 인용용 raw_text는 문맥줄 없이 따로 보관. 고아 청크("매출 3% 증가")가 어느 회사·기간·섹션인지 임베딩에 녹아 검색 정밀도가 오른다. LLM 미사용 → 비용 0.

  1. ① 계약 변환 — contract.to_internal이 v2.0 ChatV2Request(roomId·companyContext·messages)를 내부 ChatRequest로 번역한다. messages의 마지막이 현재 질문, 나머지는 단기 메모리(history, 최근 10개).
  2. ② 라우팅 — router_agent(gpt-4o-mini)가 RouterResult를 낸다: intent(qa/summary/smalltalk/out_of_scope), search_query(회사명·말투 제거한 정제 키워드, 공시 용어로 풀어씀), financial_relevant/macro_relevant 플래그, 기간(date_from/to), prefer_recent. "위험 요소"→"사업위험 시장위험 재무위험관리"처럼 terse 입력을 검색 친화적으로 확장하는 게 핵심.
  3. ③ 분기(가드) — smalltalk면 reply로 짧게, out_of_scope(다른 회사/비교)면 안내 문구로 즉시 응답하고 검색·작성·검증을 건너뛴다(불필요한 LLM·검색 절약).
  4. ④ 병렬 검색·결합 — asyncio.gather로 동시 실행: ⓐ corpus 하이브리드 검색(벡터∪BM25 RRF), ⓑ 재무 결합(financial_relevant일 때 DART fnlttSinglAcnt), ⓒ 거시 결합(macro_relevant일 때 ECOS). return_exceptions=True로 한 소스가 실패해도 나머지로 진행(graceful). 재무 정형수치(score=1.0)는 앞에 배치해 항상 상위 근거로 포함된다. 가장 느린 하나만 기다리므로 지연 영향 최소.
  5. ⑤ 작성(retrieve-then-read) — 검색·결합된 근거를 프롬프트 텍스트로 만들어 writer(gpt-5.1)(qa) 또는 summary(gpt-4o-mini)에 넣는다. 에이전트는 근거 안에서만 답을 쓰고(검색 툴 없음 → 환각·비결정성↓), 공통 _PERSONA로 말투를 일정하게, 수치는 출처 콤마 표기·근거 기수 그대로 쓴다.
  6. ⑥ provenance 고정 — 응답의 출처는 에이전트가 고른 게 아니라 코드가 검색한 실제 근거(citations[:5])로 고정한다(인용 환각 차단).
  7. ⑦ 검증 — _should_verify(verify_sample_rate=1.0이면 매 턴)면 verifier(o4-mini)가 답이 근거에 충실한지 grounded_score(0~1)를 매기고, verdict(pass/partial/fail)는 코드가 임계값(0.7/0.4)으로 확정(모델 라벨 변동 제거).
  8. ⑧ 응답 변환·보관 — contract.to_v2가 내부 결과를 v2.0 ChatV2Response(answerText·sourceContent·sources·macroSnapshot·verification)로 번역하고, 근거 있는 답이면 storage.save_chat으로 SQLite에 보관(→ 목록/상세 조회).

6-3. 하이브리드 검색 (진짜 하이브리드)

BM25는 어떻게 점수를 매기나 (키워드 검색의 원리)
"검색어가 이 문서에 얼마나 잘 맞나"를 세 가지로 계산한다:
  1. 단어 빈도(TF) — 검색어가 문서에 많이 나올수록 점수↑. 단 너무 많으면 효과가 점점 둔해짐(포화).
  2. 희소성(IDF) — 흔한 단어("회사·것")는 가중치↓, 드문 단어(300,870,903·"하만")는 가중치↑. 드문 핵심어가 진짜 신호니까.
  3. 문서 길이 보정 — 긴 문서는 단어가 많이 나오는 게 당연 → 길이로 정규화해 짧은 문서가 손해 안 보게.
한마디로 "드문 핵심어가 · 짧은 문서에 · 적당히 나오면" 높은 점수. 그래서 정확 수치·고유명사·티커에 강하고, 벡터(뜻) 검색이 놓치는 "글자 그대로 일치"를 잡아준다. (벡터=뜻, BM25=글자 → 둘을 합친 게 하이브리드)
# rag/vectorstore.py::VectorStore.search (요지)
vec_ids  = coll.query(query_embeddings=[q], n_results=candidate_k, where=...)   # 벡터 후보
bm25_ids = 전체 코퍼스 BM25 top-k (지연 캐시, where 동일 적용)                   # 정답이 벡터 밖이어도 포착
# RRF 융합 (bm25_weight=0.5, _RRF_K=60)
score[id] = (1-w)/(60+rank_vec) + w/(60+rank_bm25)
# 0~1 정규화(상위=1.0) → rerank(중복제거 + 최신우선) → top_k

이전 — 가짜 하이브리드

BM25가 벡터 후보 20개 안에서만 재랭킹 → 정답이 벡터 top-20 밖이면 유실

현재 — 진짜 하이브리드

벡터 top-k 와 전체 BM25 top-k의 합집합을 RRF 융합 → 한쪽에만 있어도 생존. 숫자 토큰(300,870,903) 보존 토크나이저

6-4. End-to-End 워크스루 — 3가지 시나리오

한 질문이 들어와서 답이 나가기까지 실제 값으로 따라가 본다. 질문 종류마다 흐르는 길이 다르다.

시나리오 A — 정확 수치 (재무 결합) · "삼성전자 영업이익 알려줘"

  1. 요청 — React→Spring→FastAPI로 {roomId, companyContext:{corpCode:"00126380", corpName:"삼성전자"}, messages:[{role:"user", content:"삼성전자 영업이익 알려줘"}]} 도착. X-Trace-Id가 있으면 Logfire 루트 span에 바인딩.
  2. 라우터(gpt-4o-mini) — → RouterResult(intent=qa, financial_relevant=true, macro_relevant=false, search_query="영업이익", out_of_scope=false). "영업이익"이라 재무 플래그 ON.
  3. 병렬 검색·결합 — asyncio.gather로 동시에: ⓐ corpus에서 "영업이익" 하이브리드 검색(손익계산서 등 근거), ⓑ 재무 결합이 DART fnlttSinglAcnt(00126380) 호출 → 연결 영업이익 행을 score=1.0 citation으로 만들어 맨 앞에 배치. quote 예: "영업이익: 제 57 기 43,601,051,000,000 / 제 56 기 32,725,961,000,000 (단위 원, 연결, 2025 사업보고서 기준)", rcept_no=실제 접수번호.
  4. 작성(writer gpt-5.1) — 재무 citation을 1급 근거로 받아 페르소나·콤마표기·근거 기수로: "삼성전자 영업이익은 제 57 기 43,601,051,000,000원, 제 56 기 32,725,961,000,000원입니다."
  5. provenance 고정 + 검증 — 출처는 코드의 실제 근거(citations[:5])로 고정. verifier(o4-mini)가 grounded_score≈1.0 → 임계값으로 verdict=pass.
  6. 응답·보관 — contract.to_v2가 answerText+sources[](rceptNo·dartUrl 포함)+ verification{verdict:"pass", groundedScore:1.0}로 변환, SQLite 보관. 프론트는 "정확도 100%"와 출처 카드(+DART 링크)를 표시.
A 한 줄 흐름  질문 → 라우터(qa·재무ON) → 병렬[corpus + DART 정형재무] → writer → 검증 → 응답. 정확 숫자는 RAG가 아니라 정형 API가 책임.

시나리오 B — 요약 (사전요약 트랙) · "삼성전자 사업 내용 요약해줘"

  1. 라우터 — → intent=summary, search_query="사업 내용 반도체 디스플레이". 재무·거시 플래그 OFF(개념 질문).
  2. 사전요약 검색 — corpus·재무·거시를 안 탄다. 대신 summary_<삼성>에서 완성 요약 top-8을 의미검색. 예: "DX/DS/SDC/Harman 부문…", "메모리 기술 리더십…". (사전요약이 없으면 corpus 실시간 RAG로 자동 폴백)
  3. 작성(summary · gpt-4o-mini) — 요약 조각들을 종합 → "삼성전자는 DX·DS·SDC·Harman 등 부문으로 구성되며, 메모리·디스플레이 등 …"
  4. 검증·응답·보관 — 출처는 요약 조각(섹션·rcept_no·dartUrl), verdict=pass, 보관.
B 한 줄 흐름  질문 → 라우터(summary) → summary_<corp> 1번 검색(완성 요약) → writer → 응답. 병렬 결합 없이 빠르고 깔끔(비싼 요약은 빌드때 끝남).

시나리오 C — 거시 결합 · "요즘 환율·금리 상황에서 삼성 실적 어때?"

  1. 라우터 — → intent=qa, financial_relevant=true, macro_relevant=true, search_query="실적 매출 영업이익".
  2. 3중 병렬 결합 — asyncio.gather로 동시에: ⓐ corpus 검색 ⓑ 재무 결합(DART) ⓒ 거시 결합(ECOS) → 거시 스냅샷 예: 환율 1,535원 · 기준금리 2.5% · 국고채 3.81% · KOSPI … (과거값은 날짜별 캐시).
  3. 작성 — 공시 실적 + 거시 스냅샷을 "같은 시점의 사실"로 결합(‘환율 때문에~’ 같은 인과 단정은 피함).
  4. 응답 — macroSnapshot 필드가 채워져 프론트에 거시 표가 함께 노출 + 출처 카드.
C 한 줄 흐름  질문 → 라우터(qa·재무·거시ON) → 3중 병렬[corpus + 재무 + 거시(ECOS)] → writer → 응답. 거시 브랜치가 추가되고 macroSnapshot이 따라붙는다.

# 모든 답변이 공유하는 말투 규칙 (한 곳에서 정의)
_PERSONA = "[역할·말투—공통] 정중한 존댓말 · 서론 없이 본론부터 · 이모지/느낌표 금지 · 사실 중심 …"

def _m(name): return f"openai:{name}"     # 모델명 → provider 경로 (키는 .env)

# ── 5개 에이전트: 모델 + output_type + (지시문 = _PERSONA + 고유지시) ──
router_agent = Agent(_m(_s.router_model),          # gpt-4o-mini
    output_type=RouterResult,
    instructions=_PERSONA + "너는 라우터다. 의도(qa/summary/…)·검색쿼리·플래그를 정한다 …")

qa_agent = Agent(_m(_s.qa_model),                  # gpt-5.1
    output_type=QAResult,
    instructions=_PERSONA + "너는 공시 분석가다. [근거]만 사용해 답한다. 수치는 콤마 표기 그대로 …")

verifier_agent = Agent(_m(_s.verification_model),  # o4-mini
    output_type=VerificationResult,
    instructions="너는 검증자다. 답이 근거에 충실한지 grounded_score를 매긴다 …")  # _PERSONA 없음(채점만)

# ── 호출 (services/chat.py) — 검색은 코드가 끝내고 근거를 프롬프트로 (retrieve-then-read) ──
qa = (await qa_agent.run(f"[질문]\n{q}\n\n[근거]\n{evidence}")).output   # → QAResult (검증·자동재시도)

→ _PERSONA + "고유지시" 한 줄로 말투를 공유하고, output_type이 결과를 스키마로 검증한다. 말투를 바꾸려면 _PERSONA 한 곳만.

7-1. 관용구 — 모듈 레벨 1회 정의 + retrieve-then-read

# agents/agents.py — 모듈 로드 시 1회 생성(재사용)
qa_agent = Agent("openai:gpt-5.1", output_type=QAResult, instructions=_PERSONA + "근거 안에서만 답…")

# services/chat.py — 검색은 코드가 끝내고(retrieve), 근거를 프롬프트로 넣어 읽게(read)
evidence = format_citations(citations)
qa = (await qa_agent.run(f"[질문]…[근거]\n{evidence}")).output   # 에이전트는 작성만
왜 — 에이전트에 검색 툴을 주면 (a)환각 (b)비용↑ (c)비결정성. 검색을 코드가 결정적으로 끝내면 근거가 고정돼 재현 가능·저렴(실무 정확성-우선 RAG의 표준).
7-2. output_type
Agent(output_type=QAResult)면 출력이 스키마로 검증되고 틀리면 자동 재시도. JSON 깨짐/필드 누락을 프레임워크가 막음.
7-3. provenance 고정
에이전트가 인용을 못 지어내게, 출처는 코드가 검색한 실제 근거(citations[:5])로 고정. 재무 정형수치가 앞에 배치돼 항상 포함.
7-4. verifier 샘플링+임계값
검증 빈도는 verify_sample_rate(현재 1.0). verifier는 grounded_score만 매기고 verdict는 코드가 임계값(0.7/0.4)으로 확정(결정적).
7-5. 공통 페르소나
4개 에이전트가 _PERSONA(존댓말·차분·서론 금지·사실 중심) 공유 → 모델이 달라도 말투 일정. 수치는 출처 콤마 표기 그대로, 기수는 근거 명칭 그대로. (↓ 7-5-1 실제 내용)

  1. 어떻게 적용하나 — 각 에이전트 정의에서 지시문 앞에 붙인다: instructions = _PERSONA + "(에이전트별 고유 지시)". router·writer(qa)·summary·section_summary가 공유한다 (verifier는 채점만 해서 제외). 그래서 모델이 gpt-5.1이든 gpt-4o-mini든 같은 말투가 나온다.
  2. 수치·기수 규칙은 따로 — writer/summary 지시에 추가로: "정확 수치는 출처의 콤마 표기 그대로(43,601,051원), '43조 6,010억' 같은 조/억 변환 금지. 기수는 근거에 적힌 명칭(제57기)을 그대로." → 답마다 숫자 표기가 흔들리던 것도 고정.
  3. 왜 한 곳에 — 말투·역할·규칙을 바꾸려면 _PERSONA 한 곳만 고치면 전 에이전트에 일괄 반영. (기존 CrewAI는 backstory가 함수마다 흩어져 있어 일관성 맞추기 어려웠음 — §11·§16-4)

7-6. 복합·멀티턴 질문은 어떻게 처리되나

"한 번에 2가지를 묻거나", "이전에 물어본 걸 이어서 묻거나", "도중에 다른 트랙으로 바꿔 묻는" 경우의 처리.

  1. 복합 질문 (한 번에 2가지) — 라우터는 intent 1개 + 플래그(financial_relevant·macro_relevant)를 정한다. 예: "매출 얼마고 환율 영향은?" → intent=qa + 재무 + 거시 플래그 → corpus·재무·거시를 병렬 결합해 writer가 통합 답. 한계: intent는 1개라 "요약 + 정확수치" 혼합이나 서로 다른 주제 2개("위험요소와 배당정책 비교")는 단일 라우팅이라 약함 → 추후 에이전트 쿼리 분해(시나리오 D)로 보강(§15).
  2. 멀티턴 (이전 질문 이어받기) — 최근 대화(history)를 라우터·writer에 함께 넘긴다. 라우터가 생략된 주어·지시어("그럼 매출은?", "그거 더 자세히")를 직전 맥락으로 해석해 search_query를 정제하고, writer도 history로 "그거/방금"을 푼다. 행동 평가의 멀티턴 케이스로 검증됨.
  3. 도중에 다른 트랙으로 전환 — 라우터는 매 턴 새로 분류한다. 같은 방에서 이전엔 요약을 묻고 지금은 정확수치를 물으면 intent·플래그가 그 턴에 맞게 바뀐다(summary→qa, 재무 플래그 ON 등). 트랙은 턴마다 독립적으로 결정되고, out_of_scope(다른 회사) 가드도 매 턴 적용된다.
  4. 상태는 누가 갖나 — AI는 stateless. 세션·대화이력은 백엔드가 소유하고 매 요청의 messages로 넘긴다(마지막=현재 질문, 나머지=history 최근 10개). 그래서 AI는 같은 입력에 같은 출력(재현 가능).

8요약은 어떻게 이뤄지고 활용되나 핵심

핵심 — "비싼 요약은 빌드때 1번, 질의때는 꺼내쓰기만". 각 공시의 섹션을 미리 요약해 summary_<corp> 컬렉션에 저장하고, summary 질문은 그 완성 요약을 검색한다(사전요약 트랙, 구현 완료).

8-1. 무엇을 기준으로 요약하나 (criteria)

  1. ① 단위 — 섹션(목차)별 DART 섹션 계층을 단위로. micro-섹션은 ~6,000자 묶음으로 합치고 공시 1건당 ~40묶음 상한(summary_section_target_chars·summary_max_sections), 200자 미만 스킵.
  2. ② 가중 — 분석 가치 높은 섹션 우선 사업의 내용·경영진단(MD&A)·위험·주석·주요계약·연구개발을 올리고, 정관·임원명부·계열회사 같은 형식 섹션은 제외/후순위(summarize._weight). 표는 제외(수치는 RAG/재무 담당).
  3. ③ takeaway 지시 "실제 내용(사업·전략·리스크)을 3~6문장으로. 목차식 메타설명 금지, 정밀 수치 망라 금지(대표 1~2개만)." → 요약=서술 담당, 정확 수치=corpus/재무 담당으로 역할 분리.

현재는 "기본"(섹션+가중+takeaway). 변화탐지·이벤트트리거는 추후 고급 단계(§15).

8-2. 데이터 흐름 — 빌드(생성) → 질의(소비)

[빌드 타임 · 1회 ~$1-2]  DART 원문 → 파서(Block) → 섹션 묶음(가중) → gpt-4o-mini 요약
                      → 임베딩 → summary_<corp> 컬렉션 저장 (corpus와 별개 저장소)
[질의 타임 · summary 질문]  router(intent=summary) → summary_<corp> 벡터검색(완성 요약 top-k)
                      → summary_agent가 종합 → 답 (출처 rcept_no·섹션·dartUrl 유지)
                      → 사전요약이 없으면 기존 corpus 실시간 RAG로 자동 폴백
저장소가 2개로 분리: corpus_<corp>(원문 청크·정확사실·QA) + summary_<corp>(사전요약·개요). qa(정확수치)·재무·거시·verifier·v2.0 계약·보관은 그대로 — summary 트랙만 바뀐다. 폴백이 있어 점진 적용이 안전.

8-2-1. "corpus 폴백"이 정확히 하는 일 (상세)

summary 질문이 들어오면 항상 summary_<corp>를 먼저 뒤진다. 거기서 결과가 안 나오면 corpus로 폴백한다.

  1. 언제 발동하나 (정확한 조건) — search_summaries()가 빈 리스트를 돌려줄 때만. 그건 곧 summary_<corp> 컬렉션이 없거나(미빌드) 비었을 때다. 주의: 벡터 검색은 컬렉션에 데이터만 있으면 어떤 질문이든 항상 top-k(가장 가까운 것)를 돌려준다. 그래서 "질문에 딱 맞는 요약이 없어서"가 아니라 "그 회사가 아직 사전요약 안 됨"이 유일한 발동 조건이다.
  2. 무엇을 하나 — corpus_<corp>에서 원문 텍스트 청크(kind=text 필터) top-8을 검색해 가져온다. 이건 완성 요약이 아니라 원문 그대로다. → 그 원문 청크들을 summary_agent에 [근거]로 넣어 질의 시점에 요약을 새로 생성한다(= 사전요약 도입 전의 '실시간 RAG 요약' 방식).
  3. 왜 있나 (안전장치) — 점진 적용을 위해서다. 새 회사를 추가하고 build_summaries를 아직 안 돌렸어도 요약 질문이 깨지지 않고 동작한다(옛 방식으로라도). 사전요약을 켜고 끄는 게 자유롭다.
  4. 현재 상태 — 삼성·현대 둘 다 빌드돼 있어 폴백은 실제로 안 탄다 — 항상 사전요약을 쓴다. 폴백은 "보험".
  5. 트레이드오프 — 폴백은 매 질의마다 재검색+재요약이라 느리고 비싸다(사전요약의 장점이 사라짐). 그래서 폴백은 어디까지나 비상용이고, 정상 경로(사전요약)가 빠르고 안정적이다.
두 경로의 차이 = summary_agent에 넣는 [근거]가 무엇이냐 (최종 답은 둘 다 summary_agent가 쓴다)
정상 (사전요약 트랙)폴백 (corpus)
근거이미 만든 완성 요약 조각원문 텍스트 청크(요약 안 됨)
요약 시점빌드때 (미리, 1회)질의때 (즉석, 매번)

9백엔드 연동 — v2.0 계약 · X-Trace-Id

9-1. AI는 stateless — 책임 분리

통합 구조에서 AI(FastAPI)는 추론만 담당하는 stateless 서비스다. 백엔드(Spring gongsitoktok-spring)는 POST /api/v1/chat 하나만 호출하고(FastApiChatClient), 그 결과의 보관·목록·상세(마이페이지)는 백엔드가 자체 DB(QaHistory)로 직접 처리한다. 대화 세션·이력도 백엔드 소유.

책임담당

보관·목록·상세(마이페이지)백엔드(gongsitoktok-spring) — QaHistory 엔티티 + 자체 DB

9-2. v2.0 계약 (백엔드 gongsitoktok-spring 드롭인 호환)

내부 스키마와 분리된 camelCase 와이어 계약을 contract.py 어댑터로 변환 → 백엔드 코드 수정 없이 연동.

요청  ChatV2Request : { roomId, userSeq, companyContext:{corpCode,corpName}, messages:[{role,content}] }
응답  ChatV2Response: { roomId, intent, answerText, sourceContent, macroSnapshot,
                       sources:[{rceptNo,reportNm,rceptDt,sectionTitle,quote,score,dartUrl}],
                       outOfScope, detectedCompany, needsClarification,
                       verification:{verdict,groundedScore}, error }
verification.groundedScore(0~1) = 답변 1건의 최종 정확도(프론트 "정확도 %"). sources[].score = 출처별 검색 관련도(0~1 정규화). dartUrl = DART 원문 링크.

9-3. X-Trace-Id 端-to-端 추적

백엔드가 보낸 X-Trace-Id를 응답 헤더로 echo + Logfire 루트 span에 바인딩. 그 아래 AI 내부 호출(router→검색→writer→verifier)이 자식 span으로 묶여, 백엔드 trace_id 하나로 AI 추론 과정까지 추적(금융권 감사가능성). 관찰성 off면 no-op.

12-1. 어떤 기준으로 케이스를 구성하나

각 케이스 = 질문(또는 검색쿼리) + 기대(expect) + 중요도(severity). JSON 한 줄로 추가·관리한다.

  • 중요도(severity) — must=하드 통과 기준(하나라도 실패면 FAIL), watch=알려진 약점(미통과 허용, 추적용). 합격률은 must로만 집계.
  • 케이스 선정 — ① 핵심 동작(요약·정확수치·스코프) ② 어려운 케이스(멀티턴·거시·표질의·되묻기·비교) ③ 약점 추적(watch). 회사는 삼성·현대 둘 다.

기대(expect) — assertion 종류

assertion뜻
intent라우터 분류가 기대와 같은지(qa/summary/smalltalk/out_of_scope)
contains_any답·근거에 이 문자열 중 하나라도 포함(키워드/수치)
has_number콤마 숫자 토큰 포함 여부(값은 안 고정 → 신선도)
verdict_not이 verdict면 실패(예: fail 금지)
out_of_scope / macro_used / needs_clarification / no_citations스코프 가드 / 거시 결합 / 되묻기 / 근거없음(스몰토크) 동작 확인
expect_any (검색)top-k 결과의 섹션·인용에 이 문구가 있으면 hit (hit@k·MRR 집계)

"지역별 매출"이 엉뚱한 주주현황을 잡음RRF 가중 0.6/0.4라 벡터 후보 5개가 BM25 1위보다 높아 top-5가 사실상 순수 벡터동등 가중(0.5)으로 1:1 교차. 융합 가중이 한쪽을 묻으면 하이브리드가 아님
"삼성랑 SK 비교"가 out_of_scope로 안 걸림방 회사(삼성)가 같이 언급돼 in-scope로 오판. 기존 골든은 순수 타사라 못 잡음라우터에 비교 질문 규칙 추가. 행동 평가(eval)가 이 버그를 잡음
답마다 말투·도입부가 제각각, 기수(제56/57기) 오기답 주체 4개가 페르소나 미공유 + 재무 근거에 기수 명칭 없어 모델이 추측공통 _PERSONA + 재무 quote에 실제 기수(thstrm_nm) 포함. 일관성은 공유 규칙 + 근거 명시로
verifier verdict가 런마다 pass↔fail 변동모델이 verdict 라벨을 직접 매겨 비결정적grounded_score만 받고 verdict는 코드가 임계값(0.7/0.4)으로 확정. 판정은 결정적으로
교훈 요약 — ①에이전트엔 "작성"만 맡기고 출처·판정은 코드가 고정 ②융합·분할엔 안전장치 ③일관성은 공유 페르소나+근거 명시 ④좋은 eval이 진짜 버그를 잡는다.
